# AGENTS.md — AudioSleuth

## 1. Project Identity

**Project Name:** AudioSleuth — Digital Audio Forensics Toolkit  
**Academic Subject:** Cyber Security and Digital Forensics (CSDF)  
**Academic Context:** SPPU, Pune Institute of Computer Technology (PICT)  
**Project Type:** Academic mini-project  
**Primary Objective:** Design and develop a working tool for the forensic examination of digital audio recordings.

## 2. Project Description

AudioSleuth is a local-first digital audio forensic analysis application that helps an investigator examine audio files, verify file integrity, visualize signal characteristics, identify potentially suspicious audio segments, and generate structured forensic reports.

The tool will combine digital evidence handling, audio signal processing, anomaly detection, visualization, and report generation in one user-friendly interface.

The system must be functional, explainable, reproducible, and suitable for an academic demonstration.

This is an investigative assistance tool, not a certified forensic laboratory system.

## 3. Core Objectives

1. Accept supported digital audio files as evidence.
2. Preserve original evidence and record its cryptographic hash.
3. Extract available audio properties and file metadata.
4. Visualize waveforms, spectrograms, and frequency characteristics.
5. Detect potentially suspicious signal patterns using explainable signal-processing methods.
6. Localize flagged intervals using start and end timestamps.
7. Store case information, analysis results, and audit events.
8. Generate downloadable forensic reports.
9. Support comparison against a reference SHA-256 hash or another audio recording.
10. Provide an intuitive, professional interface suitable for a live academic demonstration.

## 5. Functional Requirements

### 5.1 Evidence Intake

Implement:
- Drag-and-drop and file-picker uploads.
- A configurable maximum upload size.
- Supported-format validation.
- Safe filenames and server-generated evidence identifiers.
- Upload error handling and clear status messages.
- Evidence registration before analysis.

Support WAV, MP3, FLAC and other formats only when the required decoder is available and verified.

Never trust the filename or extension alone. Validate the actual content and handle malformed files safely.

### 5.2 Evidence Integrity

For every evidence item:
- Compute SHA-256 from the exact uploaded bytes.
- Record the digest, file size, upload timestamp and generated evidence ID.
- Preserve the original evidence bytes unchanged.
- Perform decoding and signal processing on a separate working representation.
- Recalculate the stored original's hash when verifying integrity.
- Display a clear match or mismatch result when comparing against a reference hash.

Distinguish file integrity verification from authenticity verification. A matching hash confirms that the compared bytes match; it does not establish who created the recording or whether the recording was manipulated before acquisition.

Maintain an audit trail for relevant actions, including uploads, analyses, integrity checks and report exports.

### 5.3 Metadata and Audio Properties

Extract and display, where available:
- Filename and file format
- File size
- Duration
- Sample rate
- Number of channels
- Sample format and bit depth, when reliably available
- Codec and bitrate, when available
- Available embedded metadata
- SHA-256 digest

Label unavailable properties as unknown or unavailable. Do not fabricate metadata or infer recording time from filesystem timestamps.

Clearly distinguish metadata embedded in the file from metadata generated by the application.

### 5.4 Audio Visualization

Implement:
- Interactive waveform visualization.
- Time-frequency spectrogram.
- Frequency spectrum.
- Audio playback controls.
- Current playback time.
- Timestamp selection and navigation to flagged intervals.
- Zooming or region selection where practical.

Charts must use actual data computed from the uploaded audio, not hardcoded sample values.

For long recordings, use bounded processing, suitable downsampling for visualization, and asynchronous backend tasks where appropriate.

### 5.5 Forensic Signal Analysis

Implement explainable, configurable analysis methods.

**A. Silence and low-energy interval detection**
- Calculate short-time RMS energy.
- Identify intervals below a configurable threshold.
- Apply a configurable minimum duration.
- Report start time, end time and measured energy.

**B. Abrupt amplitude transitions**
- Measure adjacent-sample or short-window changes.
- Flag unusually large discontinuities.
- Avoid treating normal transients as definitive tampering.

**C. Spectral inconsistency**
- Calculate short-time Fourier transform features.
- Compare spectral characteristics of adjacent frames.
- Flag unusually large changes using documented thresholds.

**D. Short-time statistical analysis**
- Calculate relevant windowed statistics, such as RMS, peak amplitude and spectral flux.
- Display plots and explain how the selected measurements contribute to each finding.

**E. Repeated-segment investigation**
- As an advanced feature, compare feature representations of audio segments to identify potential repetitions.
- Avoid naive whole-recording self-similarity comparisons that create excessive computation.
- Clearly identify this feature as exploratory unless validated on a suitable test dataset.

Every detection method must document its algorithm, parameters, threshold selection and limitations.

### 5.6 Findings and Risk Interpretation

Each finding must include:
- Finding ID
- Detection method
- Start and end timestamps, where applicable
- Measured feature or score
- Applied threshold
- Reason for flagging
- Suggested manual review action

Use labels such as:
- No configured indicator detected
- Potentially suspicious interval
- Manual review recommended
- Analysis incomplete

Do not claim that an audio file is definitively authentic, fake, AI-generated, or tampered with based only on simple signal anomalies.

Do not invent probabilities, accuracy percentages, model confidence, or forensic conclusions.

### 5.7 Case Management

Create a case record containing:
- Case ID
- Case title
- Investigation notes
- Creation timestamp
- Associated evidence
- Analysis runs
- Findings
- Report history

Support listing, viewing, and opening cases. Provide explicit confirmation for destructive operations.

Keep case data, evidence files and analysis records linked consistently. Prevent orphaned database records and accidental evidence loss.

### 5.8 Forensic Report Generation

Generate a downloadable PDF report containing:
1. Report title and unique report ID.
2. Case information.
3. Evidence identification and SHA-256 digest.
4. Acquisition and analysis timestamps.
5. Audio properties and available metadata.
6. Analysis methods and parameter settings.
7. Flagged intervals and their timestamps.
8. Waveform or spectrogram visualizations where practical.
9. Findings and explanations.
10. Limitations and alternative explanations.
11. Integrity verification results.
12. A statement that findings are indicators requiring interpretation, not proof of tampering.

Reports must be generated from persisted analysis results. Do not fabricate findings or report that an analysis succeeded when it failed.

### 5.9 Comparison and Integrity Verification

Provide:
- Reference SHA-256 comparison.
- Comparison of two recordings using duration, sample rate, channel count and other relevant properties.
- Optional waveform or feature comparison for investigative support.

Explain that files with different hashes can still contain identical audible content due to encoding, metadata or format differences. Conversely, a matching hash is strong evidence of byte-for-byte identity between the compared files, not proof of original authenticity.

## 6. Non-Functional Requirements

- Maintain a clear separation between frontend, API, analysis engine, persistence and reporting.
- Use typed request and response models.
- Validate inputs on the server.
- Handle corrupt, empty, oversized and unsupported files gracefully.
- Keep analysis computation out of blocking request handlers.
- Provide progress indicators for long-running tasks.
- Use consistent error responses and application logging.
- Avoid exposing internal file paths or stack traces to users.
- Ensure the application runs locally with documented commands.
- Write unit tests for analysis algorithms and API tests for major workflows.
- Do not commit secrets, private evidence recordings or generated case data.
- Use accessible labels, responsive layouts and clear visual hierarchy.

## 7. Evidence Security and Privacy

- Process evidence locally by default.
- Never upload recordings to third-party services without explicit authorization.
- Do not execute uploaded files.
- Prevent path traversal and unsafe file access.
- Restrict accepted formats and decoder resource consumption.
- Protect against malformed-file resource exhaustion.
- Set configurable limits for upload size, duration, sample count and analysis workload.
- Use generated storage names instead of trusting user-provided paths.
- Keep original evidence separate from temporary processing artifacts.
- Clearly disclose that local SHA-256 hashes and application audit logs are not, by themselves, a tamper-proof chain-of-custody system.

Only use recordings that the project team is authorized to examine.

Frontend:
- Dashboard
- New Investigation
- Evidence Upload
- Evidence Details
- Audio Analysis Workspace
- Findings and Timeline
- Case History
- Report Viewer

Backend modules:
- `api`: FastAPI routes and request validation

- `schemas`: API request and response models

- `reports`: PDF and visualization export

Keep the analysis algorithms independent of HTTP routes so they can be tested directly.

- `GET /api/health`
- `POST /api/cases`
- `GET /api/cases`
- `GET /api/cases/{case_id}`
- `POST /api/cases/{case_id}/evidence`
- `GET /api/evidence/{evidence_id}`
- `POST /api/evidence/{evidence_id}/analyze`
- `GET /api/analyses/{analysis_id}`
- `GET /api/analyses/{analysis_id}/findings`
- `POST /api/evidence/{evidence_id}/verify-integrity`
- `POST /api/evidence/compare`
- `GET /api/reports/{report_id}/download`

Adjust routes where necessary, but maintain consistent API conventions and document them.

## 10. Testing Requirements

Create test recordings in a controlled test environment, including:
- A clean synthetic signal.
- A signal containing a known silent interval.
- A signal with an intentionally introduced amplitude discontinuity.
- A signal with a deliberately inserted or duplicated segment.
- Unsupported, empty and malformed input files.

Test both detection and false-positive behavior. Use deterministic generated signals for algorithm tests.

A test that introduces a known edit verifies whether the relevant detector behaves as expected; it does not establish general forensic accuracy.

Never use fabricated test outcomes as real-world detection metrics.

## 12. Definition of Done

The project is considered demonstrable when a user can:

1. Launch the frontend and backend locally.
2. Create an investigation case.
3. Upload a supported audio recording.
4. View its SHA-256 digest and available properties.
5. Play the audio and inspect its waveform and spectrogram.
6. Run signal-analysis methods and see timestamped findings derived from real audio data.
7. Review the methods and thresholds behind the findings.
8. Verify file integrity against a reference hash.
9. Reopen a saved case and access its persisted analysis.
10. Download a PDF report containing the actual analysis results.
11. Run the automated tests and follow the setup instructions from a clean environment.

**Final principle:** AudioSleuth must be an explainable digital audio investigation tool. It must preserve evidence integrity, produce reproducible measurements, distinguish observations from conclusions, and communicate uncertainty honestly.
